# DEV-008 access boundary

The existing Django User/session is the actor. A Learner is separate and has a tenant. Membership roles, verified guardian relationships, purpose consent, enrollment and expiring entitlements are persisted server records. Staff status confers no learner access. A teacher needs an exact learner/course assignment and teacher-reporting consent. A guardian cannot borrow another guardian's consent for their own access.

`authorized_resource` reloads scope records on every invocation. Call it before each protected read or effect, including every future job/stream batch. Never store its result as a reusable permission token. It returns only an authorized scope anchor; the API returns no content, answer key, identity, transcript or verification evidence. ScopedResource records bind learner, course and exact edition; they are not an implemented file store, vector index, job runner or stream. Those adapters must use the guard when introduced.

`GET /api/v1/access/resources/{uuid}/` requires a live Django session. Anonymous requests return 401. Missing or denied IDs both return 404. Query-supplied role, consent or payment flags are rejected. `GET /api/v1/account/csrf/` deliberately returns a masked CSRF token while retaining an HttpOnly cookie. No write endpoint, login/signup UI, account provisioning, consent-grant/revoke API or payment collection is introduced here. A valid CSRF token alone grants no capability.

Read checks require a positive remaining entitlement. Atomic quota reservation/consumption remains a later usage-service responsibility; this metadata read does not spend units or promise race-safe consumption. Rights/version checks on actual material remain the curriculum/ingestion boundary rather than an authority inferred from a generic anchor.

Privacy: these records contain only internal actor/scope IDs, statuses, notice/version/locale, purpose, times and opaque evidence references. Identity is used to establish relationships; consent evidence is restricted operational data, not an analytics label or log payload. No raw child information is needed in fixtures. Real-data retention/deletion schedules and lawful guardian verification require G3 review; no arbitrary retention deadline is added. No public workflow can turn an invitation, checkbox or payment into verified guardianship.

Database schema has foreign keys, positive versions, valid role/kind and consent-purpose checks, time-window checks, plus unique membership/enrollment/assignment keys. Cross-aggregate tenant/learner/course consistency is additionally checked by the live guard, including against internally inconsistent records. Forward migrations add only new tables; reverse migration removes this synthetic scope and must run before any data-bearing use is considered. Hosted integration verifies actual PostgreSQL behavior after the native pre-use gate; local tests do not use SQLite.

R051/R057/R060/R067 are supported within this boundary. R053's three-language safety suite and human owner, R056's child-facing notices/agency, counsel-approved consent, staff MFA, recovery/rate limits and public onboarding remain future work. Passing access tests does not complete those whole requirements or F3.
