# 03 — LearnHouse source and architecture audit

Audit date: 10 November 2026. Verdict: **credible LMS candidate, but do not adopt it as the proprietary tutoring pilot's core by default.** It offers much more platform functionality than DeepTutor, including an existing course AI assistant. It does not remove the need to build learner-state estimation, child/guardian relationships, safe personalization, or Egyptian curriculum versioning. Its AGPL and enterprise boundaries are material product decisions, not deployment details.

## Architecture and runtime

LearnHouse is a monorepo with Python FastAPI/SQLModel services, a Next.js/React web application, a Node collaboration service, a TypeScript installation CLI, and Playwright acceptance tests. Backend boundaries are `routers → services → db`; security lives in shared dependency and service checks. The REST prefix is `/api/v1`. Docker builds the web and collaboration applications and combines them with the API in an Alpine image. The final image bundles Python, Node, Bun, nginx, uv and PM2; `docker/start.sh` starts web/API/collaboration plus nginx. This is manageable self-hosted LMS infrastructure but substantially larger than a text-first tutoring pilot. Root execution and writable files should be reviewed and hardened before hosting minors' data. Base images/actions are version-tagged rather than digest/SHA-pinned; lockfiles help dependency reproducibility but do not constitute a supply-chain audit.

## Existing AI is more than a README claim

`ai_start_activity_chat_session()` and `ai_send_activity_chat_message()` authorize organization membership and activity readability before reserving AI credits. Session ownership is checked on follow-up messages. The helper `_authorize_activity_ai_access()` uses the same read-access mechanism that handles drafts, locks and paid access. This is a useful existing boundary, not proof that every endpoint is secure. [apps/api/src/services/ai/ai.py:37](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/ai/ai.py#L37)

`ask_ai()` calls a provider-agnostic generation layer and supports streaming. Activity chat places serialized course content in the system prompt and explicitly invites the model to use general knowledge when content is insufficient. That behavior conflicts with strict curriculum-grounded answers unless modified and evaluated. Uploaded course content must be treated as untrusted evidence; simply including it under “Course Content Context” does not prevent prompt injection. [apps/api/src/services/ai/base.py:17](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/ai/base.py#L17) [apps/api/src/services/ai/ai.py:187](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/ai/ai.py#L187)

`get_chat_session_history()` and `save_message_to_history()` use Redis. History is restricted to the last 20 messages, with a 2,160,000-second (25-day) TTL; metadata stores owner, organization and course. These are conversational sessions, not persistent student memory. Concurrent updates use read/append/write rather than an obvious atomic append in this function; simultaneous turns need a serialization/idempotency test. Missing Redis yields empty history, and ownership helper returns true when no Redis is configured—no stored history exists then, but production should require the service rather than silently lose continuity. [apps/api/src/services/ai/base.py:119](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/ai/base.py#L119)

The RAG search uses PostgreSQL/pgvector cosine distance, filters by organization and allowed courses in parameterized SQL, then filters unreadable activity chunks. Citations preserve activity/block/page or timestamp locators. This is a useful, relatively simple retrieval design. It still requires Arabic retrieval evaluation and immutable curriculum-edition filters; its current source rows belong to mutable course/activity content. [apps/api/src/services/ai/rag/query_service.py:42](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/ai/rag/query_service.py#L42) [apps/api/src/services/ai/rag/store.py:34](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/ai/rag/store.py#L34)

Indexing is debounced through a Redis sorted set with an in-app consumer and an in-process fallback. Claiming removes a job before execution. Graceful shutdown requeues known in-flight jobs; abrupt worker death after removal can lose a claim, and caught failures are logged rather than retried here. A backfill scheduler is present in the repository tree but its recovery guarantees were not exercised. Use a durable job ledger/leases and bounded retries for billable transcription and critical ingestion. [apps/api/src/services/ai/rag/queue.py:133](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/ai/rag/queue.py#L133)

DeepTutor integration would duplicate chat, providers, retrieval and possibly assessment generation. A separate tutor might still be justified for a particular validated capability, but “both have APIs” does not resolve authentication, student identity, permissions, course edition, chat state, billing or grades. Prefer one authoritative learner-state store and explicit request/event contracts over two products writing shared tables.

## Licensing and enterprise boundaries

The public root license is AGPL-3.0. Commercial subscriptions are permitted by AGPL; “commercial” does not mean “proprietary.” Modified covered software offered over a network must provide interacting users the opportunity to receive Corresponding Source under section 13. Conveying modified components adds sections 4–6 notice/source obligations. Do not remove license notices or assume private forks avoid network obligations. [LICENSE:1](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/LICENSE#L1)

The license's definition of Corresponding Source includes relevant installation/control scripts and some tightly coupled interfaces. A proprietary tutor behind HTTP is not automatically exempt: derivative-work boundaries depend on copied code, coupling and actual integration. If LearnHouse source is extracted into a proprietary monolith, obtain a suitable separate license or accept the applicable copyleft scope. Apache-licensed DeepTutor code cannot simply make the combined LearnHouse work proprietary. This is a technical risk assessment; counsel should review the exact integration and release model.

The source explicitly distinguishes `oss`, `ee` and `saas`. Ordinary SaaS plan gates are bypassed in OSS mode unless the feature is EE-only. Therefore Pro API Access labels in router code do **not** by themselves mean a self-hosted OSS user must buy Pro. At this pin, the explicit EE-only set is `sso`, `audit_logs`, `payments`, `analytics_advanced`, `scorm`, `lti`, `live_sessions`. Public core is not the separately licensed EE implementation. [apps/api/src/core/deployment_mode.py:20](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/core/deployment_mode.py#L20) [apps/api/src/security/features_utils/plan_check.py:16](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/security/features_utils/plan_check.py#L16)

`is_multi_org_allowed()` permits only EE/SaaS, and `check_ee_activity_paid_access()` returns true when EE is unavailable. In OSS this is an intentional free-access fallback, not a security bypass relative to its own free-tier design. It means **the founder must not assume OSS LearnHouse already enforces paid-course access**. Build reviewed entitlements or contract for the actual EE payment functionality. Analytics also delegates to EE and becomes a no-op without it. [apps/api/src/core/ee_hooks.py:94](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/core/ee_hooks.py#L94) [apps/api/src/services/analytics/analytics.py:1](https://github.com/learnhouse/learnhouse/blob/7dc39bc0e116437d564e4c7f96974397e913c338/apps/api/src/services/analytics/analytics.py#L1)

## Adoption decision and integration contract

For a one-subject tutoring pilot, LearnHouse is heavier than needed. It is attractive if course authoring, teacher assignments, rich delivery and an AGPL/open-core strategy are already central requirements. It is less attractive when the differentiator is personalized Arabic tutoring and proprietary learner intelligence, because that core still needs to be built and the enterprise/legal boundary adds decisions immediately.

Recommendation: keep LearnHouse as an evaluated LMS fallback/reference. Do not copy its code into a proprietary modular monolith under the assumption that small extraction avoids AGPL. If selected later, retain its upgrade path via external APIs and thin integration code after legal review; keep curriculum IDs and learner event/state exports independent.

Minimum external tutor contract if LearnHouse is adopted:

1. Server validates the real learner session and course access, then sends a signed short-lived tutor assertion with learner ID, org ID, enrollment/entitlement, curriculum edition and allowed source IDs. Never put organization admin tokens in student browsers.
2. Tutor reads approved content through a scoped adapter; it must not connect straight to mutable LMS tables or trust client-supplied org/course IDs.
3. Tutor emits immutable attempt/session events, request IDs, policy versions, skill IDs and cost records. LMS completion and inferred mastery remain separate fields.
4. Assignment integration must preserve task type, answer-key secrecy, grading rubric, revision and attempt history. LearnHouse's retry option can replace the previous submission instead of keeping history (`assignments.py:63–67`), so emit a durable attempt event before any reset.
5. Export curriculum, enrollments, attempts, consent records and learner state through documented formats; test migration to a custom platform before building deep coupling.

Estimated incremental integration work for a reviewed LearnHouse+tutor proof of concept: 2–4 focused engineering weeks, assuming infrastructure, license choice and content rights already settled.
