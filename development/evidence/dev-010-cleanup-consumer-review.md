## Scope, retries and accounting

- The worker takes an internal store and bounded batch size. It claims committed intent rows and checks the withdrawn consent binding, fixed tutoring policy, tenant, learner and optional uploader. The cutoff includes the saved pre-withdrawal generation, including zero. Each candidate is checked again against its saved upload, quota and resource bindings under lifecycle locks. Current consent, entitlement, enrollment, actor activity and active course or edition do not govern deletion. The integrator treats canonical file allocation and saved tutoring scope as original authority even if the resource's current kind, purpose or edition changes. Learner/course/tenant binding conflicts retain files and quota and leave the intent unresolved. Storage uses only the upload UUID, so identical bytes under a fresh post-regrant allocation do not collide. These guarantees assume the canonical write-once intent and upload scope are trusted persisted records. [Consumer](../../backend/modules/ingestion/cleanup.py) · [Canonical intent creation](../../backend/modules/identity/consent.py) · [Allocation](../../backend/modules/ingestion/service.py)
- A claim records an expiring lease and fence, then commits before entering ingestion. Keyset paging advances past unresolved objects, and the end-of-sweep check includes objects behind the cursor before marking complete. Three completed unresolved sweeps exhaust the automatic attempt budget and leave a redacted blocked state. Explicit replay preserves the original selector. Lease expiration makes an interrupted attempt reclaimable and does not establish writer closure. An open writer retains its reservation until the synchronous receiver closes and acknowledges it. An abandoned writer of unknown status stays blocked and charged. No proof-bearing reset or writer-crash recovery procedure was implemented. [Consumer](../../backend/modules/ingestion/cleanup.py) · [Receiver and dispatch fences](../../backend/modules/ingestion/service.py)
- Cleanup commits the terminal write fence before file I/O. Existing manifest publication holds the lifecycle locks and rechecks authority and dispatch before writing. Purge requests directory synchronization after unlinking both immutable names, then checks absence without following symlinks. Failure, partial unlink or interruption before settlement keeps the outstanding charge until a retry obtains confirmation. Settlement atomically clears the actual recorded charges and sets terminal confirmation under the same lifecycle locks. Legacy deleted rows can gain file confirmation without duplicate credit. A lost lease forbids target database mutation and progress settlement. A worker already past its pre-I/O check may finish an idempotent unlink for the same fenced UUID. ## Findings and corrections

1. A non-locking lease check left a window for a second claimant to advance the fence before the first worker settled the target. The correction holds the exact intent row after quota, upload and learner locks during target transitions, checks expiry after acquiring it, and locks only the intent for final progress. Claim and replay take no ingestion locks. The staged database probe attempts a competing expired claim while settlement holds the intent lock. [Lease handling](../../backend/modules/ingestion/cleanup.py) · [Probe](../../backend/tests/ingestion/postgres_probe.py)
2. The joined uploader read in the existing upload locking query could lock the user row before the learner in PostgreSQL. A guardian-scoped withdrawal takes the learner lock before inserting an intent whose uploader foreign key needs the user row. Limiting the query's row lock to the upload removes that competing lock order. Manual withdrawal and the receiver's file-I/O entry point now require autocommit, including when it was explicitly disabled outside an atomic block. Both use the same strict file confirmation before credit. These corrections were source-reviewed. The database-free tests exercise the autocommit precondition, and real lock-order and concurrency behavior still need PostgreSQL evidence.
