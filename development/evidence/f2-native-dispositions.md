## Restricted test boundary: conditions, not completed evidence

The local PoC configuration explicitly sets `gssencmode=disable`, `require_auth=scram-sha-256`, `sslmode=disable` with numeric loopback and generated credentials. [PostgreSQL 18 libpq documentation](https://www.postgresql.org/docs/18/libpq-connect.html) confirms that SSL disable alone would not disable GSS, and explicit required-auth excludes other negotiated methods. A future internal-only synthetic CI network is planned, not observed here. No child data, uploaded documents, attacker certificates, CMS input, KDC, kadmind, LDAP discovery or SASL plugin service belongs in this run.

Before applying any conditional scope disposition, the runner must enforce minimal ambient connection/Kerberos/LDAP/service configuration, start only owned processes, bind only the test network, use fixed generated bounded inputs and resource/time limits, and capture actual auth/SSL/GSS/runtime-library evidence. A linked dependency can be vulnerable even when the selected test does not exercise its vulnerable feature. Scope expansion, package change or new finding invalidates the proposed rationale. Unknown reachability is held, not silently accepted.

## Upstream source-version evidence and unresolved proof

The [OpenSSL 10 November 2026 primary advisory](https://openssl-library.org/news/secadv/20261110.txt) explicitly excludes upstream 3.0 for the four QUIC/AES-GCM-SIV issues listed above. It includes 3.0 for the CMS issue. Those statements support four **candidates**, not a claim that Ubuntu has adjudicated its package as unaffected: distribution feature/backport lineage still requires verification. No FIPS assumption is made.

Ubuntu records the five GnuTLS issues as vulnerable with deferred fixes despite the supplier's trust-boundary dispute. This document preserves that status. Proposed non-use of certificate validation is a scoped execution argument, not source-version exoneration. Cyrus and GSS acceptor findings also remain vulnerable where their described paths are exercised.

The strongest component/role distinction is for GSS-RPC/KDC/kadmind requests: none is part of an explicitly SCRAM-only PostgreSQL client. Still required before operational acceptance: exact source/binary path mapping for package-broad matches, no optional RPC/plugin loading, no corresponding service, clean ambient configuration, and actual controlled invocation. The two remaining libc memory-safety issues remain **held** pending native caller analysis. No fixable finding may be waived merely because the test is synthetic.

## Focused libc follow-up: static symbol evidence plan

Added `tools/security/native_symbols.py`, with three synthetic parser tests. This helper has **not been run on Linux in this review**; it makes no native-use decision. Run the reviewed backend virtualenv interpreter against the same freshly inventoried `system-native.json` before any connection. It verifies native library hashes, then records exact `readelf -WsW` output bytes/hashes for that closure, Python executable, available libpython and Python extension `.so` files found under the interpreter/virtualenv trees. It distinguishes undefined imports from definitions (libc defining a symbol is not an external caller), preserves versioned aliases, identifies wide-scanf variants and flags dynamic lookup imports. No inspected ELF object is executed or imported.

The initial primary source check is deliberately narrow: PostgreSQL tag **REL_18_6**, [fe-connect.c](https://github.com/postgres/postgres/blob/REL_18_6/src/interfaces/libpq/fe-connect.c) and [fe-auth.c](https://github.com/postgres/postgres/blob/REL_18_6/src/interfaces/libpq/fe-auth.c), inspected 15 November 2026. Searches of these two complete files found no direct `regcomp(` or `wscanf(` calls. This is not an audit of every libpq source or a build/source equivalence claim. `fe-connect.c` does implement LDAP service lookup and service-file parsing; clearing service configuration matters even with explicit connection credentials. `fe-auth.c` contains conditional GSS initiation, reinforcing why authentication controls must be explicit.

For **CVE-2026-100290**, use the resulting importers of `regcomp`/`regexec` to identify the relevant library and exact upstream function, then inspect whether its call site is confined to an excluded TLS/GSS/LDAP feature or an active fixture path. If the caller handles fixed patterns, still examine allocation-failure behavior: fixed input is not a patch. For **CVE-2026-115819**, identify imports of wide formatted input variants including ISO C99/C23, fortified and internal aliases, then inspect format string/destination sizing and whether an active test path can use the affected narrow destination conversion. A missing import cannot exclude direct/internal calls within libc or symbol lookup by string.

The helper inventories **available**, not observed-loaded, Python extensions; their transitive dependencies, optional plugins, internal calls, subprocesses and runtime dynamic lookup are not a complete process closure. Therefore a clean target-import list would narrow the remaining proof obligation, not establish whole-process safety. A positive importer must be traced; an unresolved dynamic-lookup/internal-call path remains held. Neither CVE's policy disposition changes merely because this helper or its unit tests succeeds.
