# DEV-010 private manifest return audit

21 November 2026. Baseline `fb92198aa6f3cf693682db65d42f3c96978f0ac9` on `main`. Scope was the current authored upload broker, local private storage and extraction comparator. A late authorization change can leave an in-flight authorized learner, guardian or reviewer request carrying outdated authority. No real users or data are in this stage. The initial inspection and reproduction budget was ten minutes.

## Reproduced on the authored seam

`resolve` and `review_manifest` authorize before reading the private manifest. Both verify its hash and result schema, then return text without checking whether authorization changed during the read. The snapshot obtained before the read can still provide the old hash, provenance and expiration. [Baseline broker at lines 192–230](https://github.com/EldonsLogic/sebaverse/blob/fb92198aa6f3cf693682db65d42f3c96978f0ac9/backend/modules/ingestion/service.py#L192-L230)

A local Python 3.12.13 and Django 5.2.19 probe used real `PrivateObjects` and a canonical, schema-valid one-page manifest with an authored marker. It replaced object queries with fresh in-memory row snapshots and blocked database connections. After a successful control read, the storage wrapper loaded the bytes, applied the change before returning to the broker, and returned those previously loaded bytes. Each of these three expected-denial cases returned the marker at baseline, then denied the next request.

- Resolution. The body of canonical `withdraw_consent` recorded withdrawal and incremented the learner authorization generation while the read was in flight.
- Resolution. The stored rights expiry changed to an elapsed time during the read.
- Review. The active scoped reviewer grant was removed during the read. The probe used the real grant helper with mocked query results.

Probe exit `0` means all three baseline defects reproduced as asserted. The harness ran with `PYTHONPATH=backend SEBAVERSE_ENV=local DJANGO_DEBUG=1 DJANGO_SETTINGS_MODULE=config.settings backend/.venv/bin/python -` from the repository root. No database server, scanner, parser, model or real upload was used. The probe bounds the ordering deterministically and supplies no evidence about PostgreSQL locking or timing.

## Bounded correction under R041 and R046

The correction keeps the pre-read denial checks and pins the scope, authorization generation, manifest digest and provenance before reading. After validating the bytes against those values, it reloads the upload and rechecks the current requester authority and rights for `resolve`, or the current uploader scope, reviewer grant and reviewer membership for `review_manifest`. It returns only if the refreshed upload still has the same authorized scope, state and manifest binding. Resolution continues to use the independently authorized requester. There is no database lock across file I/O. An authorization or state change visible to the final checks prevents the return. The final checks do not cancel an operation after its authorization point.

Acceptance includes a valid unchanged read, pre-read denial without file I/O, and no content return when consent, rights expiry, reviewer grant, membership, resource kind or manifest identity changes during file I/O. PostgreSQL and mandatory F3 suite results remain separately gated. ## Separate R046 integration gap

Canonical consent withdrawal fences the learner generation, which denies future reads. It does not enqueue or trigger ingestion purge. The same baseline withdrawal probe left both temporary source and derived manifest files on disk. The broker's explicit uploader `withdraw` call purges those files and releases quota on success. The authored PostgreSQL probe calls it separately after consent withdrawal. A consent-driven purge needs its own scope and durable retry acceptance, including the distinction between immediate denial and later confirmed purge. No retention deadline is inferred, and the read fence does not close R046. The local adapter creates exclusive regular files under a private root and rejects symlinks on read. No existing upload path can create a named pipe there. A blocked read on a locally substituted special file would require filesystem mutation beyond the authored upload path.
