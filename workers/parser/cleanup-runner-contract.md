# DEV-010 bounded manual consent cleanup runner

23 November 2026 · R040/R046 · AUTH-015. A misbound cleanup runner can credit quota against the wrong store or act outside the approved cohort. This slice is limited to source and authored fixtures in F3, with one review pass and up to two corrections. The management command delegates selection, fencing, purging and settlement to the existing consumer. ## Trusted configuration

`run_consent_cleanup` is a local management command with no custom arguments or scope selectors. The checked-in configuration leaves it disabled. A separately authorized synthetic setup must explicitly configure `LOCAL_MODE=True`, `CONSENT_CLEANUP_ENABLED=True`, and `CONSENT_CLEANUP_STORE` as the already-composed default `PrivateObjects` instance for the fixture database’s uploads. The only eligible database configuration is one unrouted, explicit loopback PostgreSQL default. The operator must verify that the database and store belong to the same disposable fixture installation. Loopback and an existing private directory establish neither that pairing nor runtime qualification. The command is unavailable in production mode.

The command creates no adapter, directory, namespace or lock files, and changes no permissions. It rejects a missing, relative, symlinked, substituted, nonprivate or nonowned root, along with any protected writer mode or protected-store marker. The eligible directory is the explicit absolute location configured before launch, owned by the process account with mode `0700`. The command holds one checked directory descriptor through the call and uses the existing confirmed-purge receipt relative to it. The separate protected-writer runtime remains disabled here. Active writers without closure proof stay blocked and charged. Use stable storage configuration for the full invocation.

## Bounded outcomes

Run the existing `run_batch` at most four times, each with a target limit of 25. An intent with multiple pages can account for multiple batches. Stop immediately on `None`, which can mean no due work or loss of the current lease. The summary gives counts of returned complete, pending and blocked batch outcomes and reports `no_result` or `limit`. It reports no identities, filenames, payloads or deletion counts. A runtime error uses a fixed message and ends the invocation. Earlier batches may already have committed. Any later invocation remains subject to the persisted cursor, lease, target fences and original cohort. The cap bounds work count. Database calls and filesystem operations can block, so wall-clock deadlines and supervision remain runtime qualification work.

The command uses the consumer’s transaction boundaries. It never reopens blocked intents, bypasses runtime checks or independently refunds quota. There is no installed scheduler, daemon or periodic retry. AUTH-014 supplier wait and the F3 and RISK-F3-005 boundaries remain. A command wiring check with a fake consumer proves entry-point behavior only. Actual database, storage qualification, operational scheduling and real-data retention still require their own evidence.
