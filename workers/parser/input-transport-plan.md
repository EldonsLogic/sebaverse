[PDF core](digital_pdf.py#L175), [guard](process_guard.py#L43), [result decoder](result_transport.py#L57), [ingress limits](../../backend/modules/ingestion/contracts.py#L5).

The risks are unbounded reads and accepting source bytes or scan evidence for the wrong dispatch. This increment exposes only authored fixtures to a local child. ## Proposed fixture protocol

Use one stdin frame with a four-byte `SDP1` version marker, a four-byte unsigned big-endian metadata length, up to 4 KiB of UTF-8 JSON metadata, and the original PDF bytes. The exact metadata fields are `expected`, `job_envelope`, and `scan_envelope`. `expected` is the eight-field job snapshot already required by the PDF core. The two envelopes keep their existing structure and signatures. Require an exact integer `expected.byte_count` in `[1, MAX_BYTES]`, read exactly that many raw bytes, and require EOF before invoking the core. Reject missing or trailing bytes, empty/oversized headers, malformed UTF-8 or JSON, duplicate fields at any level, floats and non-finite numbers. Bound JSON number conversion and handle malformed shapes and depth as one content-free error. The core still verifies exact field sets, HMACs, scanner binding, expiry, type, length and source hash before opening the factory. Raw bytes avoid the extra size and decoding step of base64. [Job contract](digital-pdf-contract.md).

- Proposed pure API in `workers/parser/input_transport.py`: `encode_request(data, *, expected, job_envelope, scan_envelope) -> bytes` and `read_request(stream) -> (data, expected, job_envelope, scan_envelope)`. The writer accepts trusted server-built metadata only and validates types, size and agreement with the exact source byte count before returning a frame. The reader accepts a blocking buffered binary stream and enforces header and source lengths before each bounded read. Both report `InputTransportError("invalid_worker_input")` without input text or chained decoder exceptions. Neither decides authorization nor implements cryptography.
- In `workers/parser/process_guard.py`, add an explicit internal PDF input profile to `run_worker`. Keep the generic 1 MiB absolute ceiling, the 64 KiB default, existing smaller caller limits and the output/time/error ceilings. Only the explicit profile allows an input limit up to `MAX_BYTES + 4096 + 8` bytes, or 8,392,712 bytes. Keep one process/I/O implementation. Set the profile in trusted test composition and reject any attempt to select it through the frame.
- Put the executable child under `backend/tests/ingestion/fixtures/` with a fixed authored fake document factory, fixed synthetic signing keys and scanner ID, and an optional fixed fixture clock chosen in code. Use the existing guarded `-I -u` launch. If imports need bootstrapping, derive the two fixed import roots from the repository fixture location. Accept no import root, factory, key, clock, scanner configuration or source path from stdin, argv or environment. Sign in the test parent using the existing manifest helper and distinct fixture keys. The child runs `read_request`, `digital_pdf.run_job` and `canonical(result)`. On rejection it exits nonzero with empty stdout and no raw input, text or credentials in diagnostics. The parent runs `decode_result` with its own captured expected job, independent of the framed dictionaries. [Guard contract](process-guard-contract.md), [stdout contract](transport-integration-plan.md).

## Acceptance and evidence

Own the proposed implementation paths above and `backend/tests/ingestion/test_input_transport.py`. Reuse the existing fixture process cleanup assertions and keep a separate real wall-time bound.

1. Run a real guarded child with a small authored PDF-like byte fixture and one padded to exactly 8 MiB. Have the fake factory surface a short Arabic/German notation marker taken from the source bytes. Assert exact text, page and anchor, preserved job provenance and `needs_review`, empty stderr, and a reaped child with closed pipes and removed temporary cwd. The same large payload fails before spawn under the generic profile and a one-byte-over source fails before spawn under the PDF profile.
2. Cover malformed version/length, a short or surplus source body, duplicate metadata members, wrong numeric types and metadata over cap. Verify bad source hash, mismatched scan and expired job or scan yield no result through the guarded child. Keep the existing fake-engine tests as evidence that invalid semantic inputs fail before the factory opens. Exercise one valid job B result against the caller’s job A snapshot to demonstrate the parent’s independent provenance check.
3. Cancel a guarded fixture that stalls with input pending or after reading it. Assert failure without partial output and cleanup. Run the focused tests and `make test-ingestion` on the final files and have a fresh reviewer check the limit calculations, frame rejects and trust boundaries. Record actual case counts and environment. This is synthetic transport and extraction-control evidence. Arabic PDF fidelity, scanner qualification and mandatory F3 exit suites require their own evidence.

## Root decision

Approve the explicit PDF stdin profile for authored fixtures, or defer large-source composition until a reviewed launcher can supply the broker-issued read-only PDF described in ADR-014. The fixture path needs no production entry point or launcher change. Review the production source handoff separately for an immutable worker, a one-object read capability and fresh job-specific credential provisioning. Shared HMAC verification keys also confer signing ability, so a worker given both keys can mint both envelopes. Fixed test keys prove matching and failure behavior only. Before activating a runtime, keep signing authority outside the child and qualify a verification/provisioning design that preserves the independent clean-scan requirement. Keep the parent’s live permission, generation and dispatch rechecks at the broker boundary.

The guard limits transfer and wall time and can kill/reap its owned process group. Framing allocates bounded buffers and can hold multiple copies of an 8 MiB source. Filesystem and network isolation, immutable imports, and OS-level CPU, RAM and process limits require the qualified runtime. Native SDK installation and execution, scanner or image changes, live broker activation, real data and forward phase work remain held. [ADR-014](../../architecture/adr/ADR-014-minimal-digital-pdf-poc.md), [AUTH-013](../../development/APPROVALS.md#auth-013--founder-direct-pypdfium2-text-only-poc-direction-19-november-2026).
