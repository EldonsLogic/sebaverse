# Local source-writer recovery plan

22 November 2026 · DEV-010 · R040/R046 · AUTH-015. Proposed implementation for the authored synthetic F3 slice. An abandoned receiver can strand a private original and its quota reservation. A mistaken reset can credit quota while a receiver can still create bytes. The current exposure is authored fixtures. The design budget is one bounded review with no new dependency or runtime activation. [Requirement spec](../../docs/04-curriculum-and-rag.md) · [Founder scope](../../sources/consent-cleanup-policy-instruction.md) · [Consumer evidence](../../development/evidence/dev-010-cleanup-consumer.md)

## Closure proof

Use a cooperative local filesystem lock shared by the server receiver and cleanup. The receiver acquires its shared lock **before** committing `receiving` and `writer_active`. It retains that lock across the whole interval in which it can create or modify the original, even if it has opened no data file yet. Cleanup acquires an exclusive lock through a separate open file description after it has committed an authorized, irreversible withdrawal fence. Acquiring the exclusive lock, combined with the exact protected row binding and fence, proves that the previous receiver cannot still write or open the source. Elapsed time, a missing blob, an expired cleanup lease, and operator replay grant no writer closure evidence.

The synthetic implementation uses 64 stable empty lock files selected by upload UUID modulo 64. They contain no per-upload metadata and remain in place for the lifetime of the store configuration. Shared acquisition permits concurrent receivers, including on the same stripe. An unrelated receiver on a collision stripe can defer purge until a later bounded pass. An opted-in store also takes a nonblocking exclusive lock for ordinary confirmed purge, including when a receiver might have acquired its guard and paused before committing a writer row. The fence still prevents that late receiver from opening the original. Per-upload lock files would avoid collisions and require lifecycle management to avoid stale inodes or unbounded sidecars.

The trusted opt-in `PrivateObjects(root, writer_recovery=True)` provisions the lock files before enabling protected writes. A fixed marker contains a random store namespace UUID. The namespace is published after creation and directory sync so an interrupted initial setup cannot issue protected bindings against incomplete coordination files. Open root and lock descriptors without following symlinks. Lock files must be regular, privately owned files with no alternative hard links. For active recovery, open an existing file and verify the namespace, root and lock identities from the actual descriptors. The store must never replace or remove a lock file, including during purge. A missing or changed lock namespace stops recovery. Keep the private directory descriptor pinned for the guarded source open and purge operations so the proof and storage operation address the same directory.

The adapter must explicitly support this capability on a single host and qualified local filesystem with coherent `flock` semantics. Open independent descriptors, acquire with `LOCK_NB`, and close them on every exit. Never upgrade an existing shared lock or explicitly unlock through an inherited duplicate. Descriptors are non-inheritable across `exec` and are never handed to parser/scanner children. Runtime composition must forbid forking while the receiving operation owns its descriptors. If a duplicate nevertheless retains an open file description after a process exits, exclusive acquisition remains blocked until the last reference closes. This supports reopening the same store after a process restart on the same host. Mount changes or restoration require a separately reconciled store binding. [Linux `flock(2)`, 22 March 2021](https://raw.githubusercontent.com/mkerrisk/man-pages/master/man2/flock.2) · [Darwin `flock(2)`](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/flock.2.html)

## Receiver and cleanup

1. Store the nullable, server-owned `writer_binding` atomically with `writer_active=True`. Bind the upload UUID, original receive generation, fresh attempt UUID and lock protocol version to the actual private root and stripe identities. The local identity combines the random namespace UUID with the device and inode of the opened root and lock file. Clear the binding with the active bit in matching completion. Legacy active rows retain a null binding. A malformed or mismatched binding cannot establish closure.
2. Resolve the server-owned upload identity and authorize the caller before preparing storage. Acquire the shared lock outside any row transaction. Under the existing quota → upload → learner order, recheck owner, live authority, receiving eligibility and generation, and commit the active binding. A receiver delayed before this step sees the committed fence and exits before opening the blob. A receiver delayed after this step already holds the lock, even before `open`. Enter the source write only through the scoped guard. Ensure the raw data descriptor closes on all exits, including a failed stream wrapper and interruption. Validate the exact binding and generation/status before normal publication or clearing the marker. The existing fenced receiver can acknowledge its own closed attempt without publishing. A receiver cannot acknowledge or clear another attempt. Keep the guard until this acknowledgment commits, then close it before any separate attempt to obtain an exclusive lock.
3. An existing authorized manual withdrawal or persisted consent intent fences the target under lifecycle locks and commits. Capture the withdrawal generation and protected writer binding under those locks. Retain the original receive generation in the binding across the withdrawal bump. Manifest creation continues to take the existing lifecycle row locks, so it finishes before the withdrawal fence or fails the dispatch fence before starting. A receiving upload without an applicable withdrawal remains outside this recovery path.
4. Outside the transaction, acquire a nonblocking exclusive lock on the exact root and stripe through the qualified adapter. Busy, unsupported, missing or mismatched proof leaves the target blocked and charged. After acquisition, recheck the same withdrawn target, withdrawal generation, exact writer attempt and applicable authority or still-valid intent under existing row locks. The already committed fence makes later byte creation impossible for a new receiver. When any check changes, discard the snapshot and allow a later bounded pass to reevaluate it.
5. Hold the exclusive lock through the existing original-and-manifest purge, directory synchronization, absence confirmation and final transaction. Keep the active marker and charge until that transaction verifies the same target, generation, exact writer binding and current intent authority. Clear the marker, record `purge_confirmed` and release remaining quota in the same transaction. If the process dies or the intent lease expires before settlement, replay reestablishes proof and confirms absence again. A stale lease holder cannot settle. Never wait for a filesystem lock while holding a database row lock. Purge stays outside database transactions.

Enable protected writes process-wide only after the receiving and recovery code agree on the lock protocol. Use the same trusted store configuration for ordinary upload and purge paths, including uploads that have already cleared their writer bindings. Legacy writers may finish their existing closure acknowledgment. Legacy active rows remain unrecoverable through this adapter even when their files are missing. Startup, operators and unrelated store implementations cannot pass a boolean or a timestamp as closure proof. A backend without this capability keeps the existing active-writer behavior. No PID tracking, process scan or signaling enters the application protocol.

## Evidence expected before qualification

- Pause a protected receiver after the active-row commit and before the first source open. Fence from another connection and verify recovery leaves the marker and reservation intact. Then stop the authored receiver, reopen the same store and verify exact-once confirmed purge. Repeat during a real partial write. Pause a would-be receiver before its active commit and verify it cannot recreate a purged file after resuming.
- Exercise independently opened descriptors in separate processes, contention without wait, inherited-reference behavior, close on exceptions and proof after process restart. Keep the private root fixed in each positive case. Verify wrong root and protocol, missing or substituted lock file, stale generation or attempt, unsupported capability, and legacy marker all fail closed. Verify a busy earlier target cannot prevent other eligible targets from being visited.
- Verify quota and both file names after failure, partial unlink, process restart, lease takeover and repeated settlement. Preserve new/regranted and unrelated files. Verify an active writer on the same stripe can conservatively defer recovery without counting as a purge, and a later bounded retry or authorized replay can finish.
- Record real-file fixture and independent review results. Actual PostgreSQL lock/rollback behavior and supported host/filesystem qualification require separate runtime evidence. This proposal supports local process-crash recovery. Host-power-loss durability, remote or multi-host storage, backup erasure and retained metadata policy remain outside the proposed proof.
